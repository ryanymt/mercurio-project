# Phase P05: The Echo Runner and GCP Deployment (Cloud Run, Air-Gaps, and Secret Hygiene)

## When the Rubber Meets the Cloud

Until Phase P05, Foreman ran in local Docker containers, test fixtures, and mock HTTP servers. Everything worked beautifully on localhost.

Localhost is a comfortable lie. In the real world, cloud platforms have cold starts, IAM edge proxies that strip HTTP authorization headers, audit logs that record environment variables for 400 days, and managed database users that default to superuser status behind your back.

Phase P05 was where Foreman made its first physical landing on Google Cloud Platform. To isolate infrastructure and networking bugs from language model hallucinations, we deployed an "Echo Runner": a model-less container that performs the full autonomous dance (claim token validation, git clone, commit creation, force push, and submission) with zero AI inference.

If something broke in P05, we knew with 100% certainty that it was an infrastructure or security defect, not an LLM having a bad day.

## What Was Built

Phase P05 deployed the complete end-to-end production loop in GCP:

1. Production Google Cloud Infrastructure (Terraform):
   * Cloud SQL PostgreSQL 17: Enterprise edition, `db-f1-micro` shared-core tier, private IP only via Private Services Access on `foreman-vpc`. Completely inaccessible from the public internet.
   * Callback API: Deployed as a Cloud Run service with public ingress, scaling to zero instances when idle. Protected by Cloud Run IAM invoker checks and application-level token verification.
   * Dispatcher and Migrator: Deployed as Cloud Run Jobs with Direct VPC egress (`PRIVATE_RANGES_ONLY`) to privately reach Cloud SQL.
   * Echo Runner: Deployed as a Cloud Run Job explicitly *without* Direct VPC egress.
   * Cloud Scheduler: Triggers the dispatcher job every minute.
   * Secret Manager: Manages database credentials, GitHub App private keys, and runner tokens.

2. Zero-Exposure Secret Pattern:
   * GitHub App installation tokens are short-lived (1 hour) and scoped strictly to the target project repository.
   * When launching a runner, the dispatcher creates a new secret version in Secret Manager: `github-token-<role>-<project>`.
   * The dispatcher passes *only the integer version number* (e.g. `1` or `2`) as an environment override to the Cloud Run Job.
   * The runner container boots and fetches that exact version number directly from the Secret Manager API using its own service account.
   * Older enabled versions are immediately destroyed.

3. Database Privilege Hardening:
   * Database user `migrator` owns the schema and runs DDL migrations.
   * Application user `app` has only `SELECT`, `INSERT`, and `UPDATE` on application tables (no `DELETE`, no goose migration tables).
   * Stripped `cloudsqlsuperuser` role using Terraform's `google_sql_user` with `database_roles = ["pg_read_all_stats"]`.
   * Verified via `foreman db rights` inside a live Cloud Run Job execution: confirmed `cloudsqlsuperuser = false` and `CREATE TABLE refused = true`.

4. GitHub Repository Ruleset Enforcement:
   * Installed a dedicated GitHub App on the managed project repository.
   * Applied a GitHub Repository Ruleset on `refs/heads/main` with zero bypass actors.
   * Even with `contents: write`, the App token cannot push to `main` (returning HTTP 409 and 422 errors). It can only push to `foreman/<ticket>/<attempt>`.

5. Cost Management and One-Command Pausing:
   * `make pause`: Pauses Cloud Scheduler and stops Cloud SQL's VM (`activation_policy = NEVER`), dropping running costs to essentially zero.
   * `make resume`: Starts Cloud SQL and resumes Cloud Scheduler.
   * Terraform lifecycle ignores `activation_policy` and scheduler `paused` states to prevent plan drift while paused.

## Why We Built It That Way (Design Defenses)

### 1. The Air-Gapped Runner Container
Why does the runner container job run without Direct VPC egress?

This is a fundamental security boundary. Developer and QA runners will eventually execute arbitrary code generated by AI models. If a runner container had Direct VPC egress, a compromised container or malicious dependency could scan the private subnet and attempt to connect directly to PostgreSQL on port 5432.

By provisioning runner containers without VPC egress, Google Cloud physically denies them any route to Cloud SQL. The runner can only communicate with the public internet: the GitHub API and the HTTPS Callback API. Even if an agent gains root access inside the container, it cannot reach the database.

### 2. Never Put Secrets in Cloud Run Overrides
Why did we build the numbered Secret Manager version pattern instead of passing the GitHub token as an environment variable override in `jobs.run`?

Google Cloud Run Jobs logs all container overrides in plaintext inside Cloud Audit Logs. Cloud Audit Logs have a mandatory 400-day retention period in GCP and cannot be edited or redacted. If you pass an access token in container overrides, that secret is permanently baked into your Google Cloud audit logs.

By passing only an integer version number (e.g. `version: 3`), the Cloud Run execution metadata and audit logs contain zero secret material. Secret Manager's data access logs contain only metadata, not payloads. A full audit log scan across the entire project confirmed zero token leaks.

### 3. Taming `cloudsqlsuperuser`
When you create a PostgreSQL user in Cloud SQL, Google automatically adds that user to the `cloudsqlsuperuser` role. This allows the user to create databases, alter roles, and bypass table ownership.

Attempting to run `REVOKE cloudsqlsuperuser FROM app` inside a SQL migration fails because Cloud SQL's security model restricts role revocations. We solved this by using the Google Cloud SQL Admin API via Terraform's `database_roles` field on `google_sql_user`. Setting `database_roles = ["pg_read_all_stats"]` explicitly strips `cloudsqlsuperuser` while satisfying Terraform's requirement that the role list is non-empty.

## Live Operational Discoveries

Deploying to real cloud infrastructure surfaced crucial real-world insights:

### Discovery 1: Cloud Run Strips User Token Signatures
During initial testing (Checkpoint G1), human operators attempted to call the deployed Callback API using `gcloud auth print-identity-token`. The request passed Cloud Run's edge IAM check, but the application rejected it with HTTP 401 Unauthorized.

Why? Google Cloud Run's IAM proxy automatically redacts the cryptographic signature of generic user ID tokens (replacing the signature with `SIGNATURE_REMOVED_BY_GOOGLE`) to prevent user token replay across services. In contrast, service account tokens minted specifically for the service audience pass through completely unaltered. 

We preserved security discipline: rather than disabling in-app verification, we parked the human path for Phase P06 (where a dedicated OAuth PKCE client or dual-token header pattern will be introduced) and provided operators with a secure CLI command (`foreman ticket create`) executed as a Cloud Run Job.

### Discovery 2: Cloud Run Jobs Scheduling Latency
In `us-central1`, Cloud Run Jobs exhibited cold scheduling delays of 2 to 3 minutes before the container process started executing. 

While our 5-minute initial claim lease accommodated the delay (leaving 1m44s of safety margin on Ticket 2), regional batch scheduling contention could easily exceed 5 minutes. As an immediate carry-over into subsequent phases, the initial claim lease will be lengthened to 10 to 15 minutes, with 30-to-60 second heartbeats maintaining the lease once the container is alive.
